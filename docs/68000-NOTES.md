# 68000 behaviours derived from the SingleStepTests fixtures

Everything here was established empirically from `vendor/SingleStepTests-m68000`, by decoding
fixture transaction logs and confirming the reading against the pass rate over 317,500 cases.
None of it is guesswork left unverified: where a rule is inferred rather than documented, it says so.

This is the reference for `hx68k-emu`'s 68000 core, and it is why the core is not a port of Musashi:
Musashi is instruction-accurate and models none of the following.

## Register model

`pc` is the **next prefetch address** (MAME's `m_au`), not the address of the executing
instruction. At the start of an instruction the opcode lives at `pc - 4`.

`pc` is a **full 32-bit register**. Only the address bus masks to 24 bits. This matters: an
exception vector of `0xEF72E254` leaves `pc` at `0xEF72E258`, not `0x72E258`. Masking `pc` itself
silently corrupts the address-error frame.

Effective addresses are likewise computed in **full 32 bits**. The address-error frame stacks the
unmasked address, so truncating during EA calculation loses the top byte.

The prefetch queue is two words: `ird` (executing opcode) and `irc` (next word). The fixture's
`prefetch` array is `[ird, irc]`.

```
prefetch():   ird = irc;  irc = read(pc);  pc += 2      // ends an instruction
fetchExt():   v   = irc;  irc = read(pc);  pc += 2      // consumes an extension word, ird untouched
```

## Bus

The 68000 has no A0 pin. The address bus always carries an even address and **UDS/LDS select the
byte**. A byte read through LDS returns the value in the low half of the data bus; through UDS, in
the high half. Byte writes mirror this.

Every bus access is 4 clock periods. Internal delays appear as idle cycles.

## Address error

The faulting bus cycle still runs, but AS is never asserted, so the suite records it as `re` (read)
or `we` (write). **The data bus value on those cycles is undefined on hardware.** MAME emits
whatever its internal latch held; the conformance runner deliberately does not compare it, because
doing so would test MAME's internals rather than the chip.

The 14-byte frame is written in **microcode order, not address order**:

| Order | Slot | Contents |
|---|---|---|
| 1 | SP-2 | PC low word |
| 2 | SP-6 | SR (value *before* entering supervisor mode) |
| 3 | SP-4 | PC high word |
| 4 | SP-8 | IR, the opcode |
| 5 | SP-10 | fault address, low word |
| 6 | SP-14 | special status word |
| 7 | SP-12 | fault address, high word |

Special status word:

```
SSW = (IR & 0xFFE0) | (read ? 0x10 : 0) | (in << 3) | fc
```

The stacked PC is per-instruction and is set out in full under
[Stacked PC on an address error](#stacked-pc-on-an-address-error) below. No general rule in terms of
`pc` or of the words fetched so far reproduces it.

Full timing, matching the fixtures exactly:

```
fault cycle (4) → idle(8) → 7 frame writes (28) → 2 vector reads (8)
                → prefetch (4) → idle(2) → prefetch (4)     = 62 cycles
```

After the vector is loaded the queue is refilled with two reads separated by 2 idle cycles.

## Effective addressing

- `(d8,An,Xn)` and `(d8,PC,Xn)`: the 2 index-computation idle cycles come **before** the extension
  word refill, not after.
- `-(An)` as a *source* costs 2 idle cycles. As a MOVE *destination* it costs none, because the
  predecrement folds into the write cycle.
- On an address error, whether a postincrement or predecrement is committed depends on the
  instruction as well as the size; see [Registers on a faulting access](#registers-on-a-faulting-access).

## Instruction-specific microcode

These are not derivable from a general rule; each instruction's microcode decides.

**MOVE**: read source, write destination, then prefetch. A source `(An)+` increments before the
destination EA is computed, so `MOVE.w (A5)+,(A5)` writes to the *incremented* address.

**MOVE to `(xxx).L`**: the low extension word is still in the prefetch queue when the address is
complete, so the **write happens between the two extension-word refills**, not after both.

**MOVE to `-(An)`**: prefetch happens *before* the write.

**CLR** reads the operand before clearing it (the well-known 68000 quirk), and the **prefetch
lands between that dummy read and the write**. On a data register, `CLR.l` idles 2 cycles *after*
the prefetch, not before.

**Long write word order is per-instruction.** `MOVE.l` writes the **high** word first; `CLR.l`
writes the **low** word first. Applying either globally costs roughly 15 to 45 percentage points on
the other instruction, so the core exposes both `writeLong` and `writeLongLowFirst` and lets each
instruction choose.

## Stacked PC on an address error

The value an address-error frame stacks is not derived from `pc` or from how many words have been
fetched. Each instruction's microcode decides where it stands, so the core keeps a `faultPc` that
handlers set as they reach each stage. Two layers produce every observed value.

**Operand reads** take a per-mode value, relative to the PC the instruction started with:

| Source mode | Stacked PC |
|---|---|
| `(An)`, `(An)+`, `(d16,An)`, `(d8,An,Xn)`, `(d16,PC)`, `(d8,PC,Xn)` | `pc - 2` |
| `(xxx).w`, and `-(An)` at byte or word size | `pc` |
| `(xxx).l` | `pc + 2` |
| `-(An)` at long size | `pc - 2` |

Extension words the instruction consumed *before* that operand shift every entry by two each. An
ADDI to `(d16,An)` therefore stacks `pc` where an ADDQ to the same destination stacks `pc - 2`.

**Later stages** are per-instruction:

- MOVE past its source operand stacks `pc + 2 * (source extension words)`. Into `(xxx).l` from a
  register or immediate source it stacks two more, because both address refills land before the write.
- JSR, CHK and DBcc stack `pc - 2 + 2 * (extension words)`.
- MOVEM stacks the current `pc`, since it refills every extension word it uses.
- CMPM, ADDX, SUBX, ABCD and SBCD stack `pc` on either operand.
- UNLK stacks `pc`.
- A taken Bcc stacks `pc - 2`, but BSR stacks the branch target itself: the return address is
  already pushed and the target already loaded when an odd one faults.

## The instruction word a frame stacks

The frame's IR slot, and the special status word built from it, follow IRD rather than the executing
opcode. An instruction that prefetches before it faults therefore stacks the *next* instruction's
opcode. MOVE.l into `-(An)` is the exception: its long write beats the instruction register to the
new opcode, so a fault there stacks the instruction's own word.

## Registers on a faulting access

Whether an address register keeps its adjustment depends on the instruction, not on a general rule:

| Case | Commits |
|---|---|
| Source `(An)+`, word | yes |
| Source `(An)+`, long | no |
| MOVE destination `(An)+` | no |
| MOVE.l destination `-(An)` | no |
| MOVE.w destination `-(An)` | yes |
| CMPM source `(An)+` | yes, and a long advances by the one word it got through |
| CMPM destination `(An)+` | no |
| ADDX, SUBX and the BCD pairs, `-(An)` at long size | no |
| MOVEM transfer that faults | the register keeps its old value |

## Flags a long move settles in halves

MOVE.b and MOVE.w have all four flags in place before the data goes out. MOVE.l settles them in two
halves whose timing depends on the operands, which is visible only in the SR a faulting write stacks:

- V and C clear as a memory source is read, or in the step a `-(An)` or absolute destination spends
  on its address. With a register source into `(An)`, `(An)+`, `(d16,An)` or `(d8,An,Xn)` they are
  still untouched when the write faults.
- N and Z are in place before the write unless the write follows the source read immediately, which
  is the case for `(An)`, `(An)+` and `(xxx).l`. In those the data path still holds the low word, so
  a faulting write stacks an N taken from bit 15 of the value.

## Packed decimal

The fixtures implement the correction over the plain binary result rather than over nibble partials,
and that difference shows on operands that are not valid BCD:

```
ABCD:  bin = dst + src + X
       lowFix  = ((dst ^ src ^ bin) & 0x10) != 0 || (bin & 0x0F) > 9
       lo      = lowFix ? bin + 6 : bin
       highFix = (bin & 0x1F0) > 0x90 || (lo & 0x1F0) > 0x90
       result  = highFix ? lo + 0x60 : lo          C = X = highFix

SBCD:  bin = dst - src - X
       lowFix = ((dst ^ src ^ bin) & 0x10) != 0
       lo     = lowFix ? bin - 6 : bin
       borrow = (bin & 0x100) != 0
       result = borrow ? lo - 0x60 : lo
       C = X = borrow || (lo & 0x100) != 0
```

Note the asymmetry in the last line: the high correction runs off the binary borrow alone, while the
flag also picks up a borrow the low correction produced. NBCD is SBCD with a zero destination.

N and V are documented as undefined. The hardware sets N from the result and V from the sign the
correction introduced: `~bin & result & 0x80` for ABCD, `bin & ~result & 0x80` for SBCD.

## CHK

N follows the operand's own sign, and the trap clears V and C and sets Z from the operand. The
frame's leading idle is 10 cycles when the operand is negative and the raw word comparison came out
at or below the bound, and 8 in every other trapping case. In range the instruction idles 6 cycles
*before* its final prefetch.

## Multiply and divide timing

MULU and MULS both cost `38 + 2n` cycles, where `n` counts set bits in the source word for MULU and
bit transitions in the source shifted up by one for MULS. The idle sits after the prefetch.

The divides put their idle *before* the prefetch. Both run a restoring division of fifteen counted
steps; each step that subtracts saves two cycles, and each step whose working register had already
overflowed saves two more:

```
idle = base - 2 * subtractions - 2 * carries
```

| Instruction | base |
|---|---|
| DIVU | 132 |
| DIVS, dividend and divisor both non-negative | 146 |
| DIVS, negative divisor | 148 |
| DIVS, negative dividend | 152 |
| DIVS, both negative | 150 |

A quotient the first compare rejects exits early: 6 cycles of idle for DIVU, 12 for DIVS, 14 for
DIVS with a negative dividend. DIVS can also overflow *after* the full division, and pays the full
time when it does. Every overflow exit leaves N set, Z clear, V set and C clear, N and Z included
though the documentation calls them undefined.

Divide by zero is not covered anywhere in the suite, so the trap this core takes for it is written
from the documentation and remains unverified.

## Other behaviours the fixtures pin down

- **A PC-relative operand is read from program space**, function code 2 in user mode and 6 in
  supervisor, where every other operand read uses data space.
- **MOVE.l writes the high word first, except into `-(An)`.** Every read-modify-write instruction
  writes the low word first. The predecrement operands of ADDX, SUBX and the BCD pairs are *read*
  low word first as well, and their long write-back is split around the prefetch.
- **A faulting low-word-first long write reports the fault at `addr + 2`**, the word it actually
  tried first.
- **The bit instructions cost two more cycles on a data register when the bit number is 16 or
  above**, and BCLR costs two more than BCHG and BSET throughout. BTST against an immediate operand
  costs what it does against a register.
- **JMP and JSR never refill the prefetch queue while computing their target**, since they are about
  to reload it. The return address JSR pushes goes out between the two target reads.
- **PEA pushes an absolute address before its prefetch** and every other addressing mode after it.
- **MOVEM reads one word beyond the transfer** on the memory-to-register direction, and the
  postincrement register ends at that word's address.
- **Writing SR or CCR re-reads the current instruction word** before the final prefetch, at the
  function code the *new* SR selects. ANDI, ORI and EORI to SR idle 8 cycles first; MOVE to SR and
  MOVE to CCR idle 4.
- **A privileged instruction checks its privilege before fetching anything**, so a violation in user
  mode costs no operand or immediate read.
- **TRAPV enters supervisor mode before its last prefetch**, which is why that read carries a
  supervisor function code.
- **UNLK A7 keeps the value it pulled**, the stack pointer increment being overwritten by it.

## Reset and interrupts, which the fixtures never reach

Neither path appears in the suite, so both are written from the manual and marked here as inferred
rather than measured.

- **Reset** takes the supervisor stack pointer from the long at `0x000000` and the entry point from
  the long at `0x000004`, enters supervisor mode with the interrupt mask at 7 and trace off, then
  fills the prefetch queue.
- **An autovectored interrupt** stacks the address of the instruction that would have run next,
  which is `pc - 4` once the queue holds the next opcode and the word after it. The old status
  register is stacked before the mask is raised to the interrupt's level. The vector is `24 + level`
  and no vector number is read from the bus, since the acknowledge cycle is terminated by VPA.
  The whole entry is 44 cycles, split here as 6 idle, the acknowledge cycle, 6 more idle, and then
  the ordinary six-byte frame. Only the total is documented; the split is a guess that no fixture
  can confirm.

## Suite caveats

The suite's own README flags TAS (missing the 5-cycle read-modify-write timing) and TRAPV as known
bad. Anything else that disagrees is our bug, not the fixture's.
